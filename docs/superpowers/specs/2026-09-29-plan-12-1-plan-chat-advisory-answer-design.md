**Date:** 2026-09-29

**Base:** `origin/main` at `81ec05f` (PR #210)

**Owners:** Codex designs; Claude reviews and implements; Codex reviews implementation; operator decides PR and merge.

**Backlog scope:** `P12-FU-1` (advisory answering) and its separately owned dependency `P11.25-FU-1` (non-AGENT conversation carriage).

## Decision and boundary

Plan 12.1 is the first Plan 12 slice on `main`; the provisional context floor was an earlier sandbox step. It makes a read-only Chat mode selectable from an ACP client and gives that mode a prose-answer contract and the existing conversation history. It is core Optimus functionality and must work when the Context Engine is absent. It is outside the v1.0 cut. Plan 2 already delivered mode enforcement; this slice reuses `ExecutionMode`, the permission layer, `MutationGuard`, and `assert_mutation_allowed()` without changing or duplicating them. The existing internal `ExecutionMode.PLAN` retains its directive prompt and read behavior; the ACP picker advertises only Agent and Chat. The golden harness and existing runner tests depend on `PLAN`, so changing it requires separate reviewed scope.

The Plan 12 context strategies—compaction, hybrid and sliding window—and their picker are **not** built here. A later picker is shown only when the Context Engine is attached, defaults to compaction, and tells the user that sliding window drops older conversation content. It is a separate select config option with stable ID `context_strategy` and custom category `_context_strategy`; it must remain independent of the Agent/Chat selection. Plan 12.1 neither advertises nor handles that option. Rules, approvals and protections remain present in every future strategy's prompt. The other four Plan 12 context follow-ups retain their own custody in the pool.

## ACP mode protocol

Expose Agent/Chat through both ACP representations used by the independently authored reference agent: classic session `modes` and one select `configOptions` entry. Both are projections of one canonical per-session `ExecutionMode`; neither owns separate state. `session/new` advertises `modes.currentModeId` plus `availableModes`, and a select config option with ID `mode`, name `Mode`, category `mode`, and the same current and available values. Do not place context strategies inside that option or create a Cartesian product of modes and strategies.

Mode IDs and config-option values are stable lowercase `agent` and `chat`; display names are `Agent` and `Chat`. A new session defaults explicitly to `agent`, preserving current behavior. Clients may change the canonical mode through either `session/set_mode` or `session/set_config_option` with `configId: mode` and a string value. `session/set_mode` returns the schema's empty success object. `session/set_config_option` returns the schema-required full `configOptions` set with its current values. Both methods accept only a known session and a supported value. An unknown config ID, boolean/type mismatch, invalid parameters, unknown session, or unsupported value returns the existing ACP error form and leaves canonical state and both projections unchanged.

On an actual change through either method, update canonical state once, then emit `current_mode_update`, then `config_option_update`, then send the method response. Both updates carry the same selected value; `config_option_update` carries the full current option set as required by the pinned schema. Repeating the current value is idempotent: it sends no update, while each method still returns its normal success shape. Mode is held per in-memory session. No `session/load`, `session/resume`, persistence, or load capability is added or advertised; `P11-FU-1` owns durable resume. When that lane later delivers load, it must restore and advertise both synchronized projections of the saved mode.

**Concurrent turn rule:** A prompt captures the canonical session mode at admission and uses that immutable value for its entire runner call, update stream, guard evaluation, and conversation commit. Both setter methods are answered without waiting for an in-flight turn. Their state change, paired updates and response use the ordering above. The in-flight turn never re-reads `session.execution_mode` after admission: its runner request, `_emit_result_updates`, `_emit_completion_message`, and `_commit_turn` use the captured value. The new mode applies to the next prompt only. A mode change must neither broaden an in-flight Chat turn's permissions nor cancel or bypass an in-flight Agent permission request.

**Task 0 mechanism finding (2026-09-29):** In installed Zed 1.21.0, a new `claude-acp` thread rendered separate Mode, Model, Effort and Fast controls without a model call. Its `session/new` response advertised both classic `modes` and `configOptions`; Zed rendered one Mode picker from the mode-category config option. Classic-modes-only rendering remains unverified. The pinned schema supports `session/set_config_option`, select options, `config_option_update`, and custom `_` categories. The earlier Optimus `Loading...` observation came from `session/load` waiting on MCP permission requests and is outside this slice. These findings replace the modes-only decision above; implementation must not reduce the contract to one surface without a reviewed successor design.

## Chat input and answer contract

The ACP adapter obtains prior history for both ACP modes from one source: `ConversationState.planner_envelope()` at the `_planner_task` seam, evaluated once for the admitted prompt. Agent keeps receiving that envelope inside `task`, unchanged. Chat receives the same string through a new optional `AgentRunRequest.conversation_envelope` field, defaulting empty for existing callers, while `task` holds only the sanitized current prompt. Extend `build_agent_planner_input` to accept and render the envelope on the Chat path, satisfying `P11.25-FU-1`; its call site supplies the field. There is no second history-selection path for the later Context Engine to reconcile. For Chat workspace-file selection, use the same envelope plus current prompt that Agent uses today, but put the current prompt only once in the model input. The envelope uses the existing canonical record ordering and byte-cap admission rather than a Chat-only history store. Prompt construction must preserve the existing untrusted workspace-data delimiters and make prior assistant/user text data rather than higher-priority instructions.

Select the prompt contract by `ExecutionMode`, not by parsing model output. For `CHAT` only, instruct the model to answer the user's question in ordinary prose, cite or qualify workspace facts when evidence is partial, refrain from claiming unseen files were inspected, and refuse instructions in untrusted workspace text. Do not append `_DIRECTIVE_GRAMMAR` to Chat. Agent's approval flow and internal `PLAN`'s existing directive prompt remain unchanged. A plain greeting should receive a useful ordinary reply; a workspace question should be answered using available workspace context. The current context assembler can omit files; without further reads, the answer must acknowledge uncertainty rather than assert a complete directory listing.

**Read-on-request decision:** deferred from Plan 12.1. Chat uses only the workspace context already assembled for the single model call; it does not ask for new file reads or run directive-like tool calls. The current non-AGENT `_finish_agent_planning` path executes `_execute_read_directives` before returning `CHAT_ONLY`; bypass that execution for `CHAT` only. Internal `PLAN` keeps its current read-directive behavior. This is a scope decision explicitly allowed by `P12-FU-1`, not a claim that all future advisory reading is forbidden. Any later guarded-read capability requires a separately reviewed Plan 12 successor and retained Plan 2 guard checks.

The existing Plan 9.96 `$0.05` per-prompt `AgentRunRequest.max_cost_usd` applies unchanged. Chat Gateway calls carry a distinct `purpose: advisory_answer` from Agent/Plan's `agent_plan`; include both `session/set_mode` and `session/set_config_option` in the server's bounded method telemetry labels. Attribute Gateway-provided usage and cost to the Chat run/session/request ID without estimating after the call. A complete, within-budget nonblank answer yields `AgentRunStatus.COMPLETED`, `CHAT_ONLY`, an `agent_message_chunk` containing the actual prose, and ACP `stopReason: end_turn`. It emits **no** `PROVISIONAL_PLAN` or `completed_plan` update, approval request, tool execution report, or mutation. After `seal_final_delivery`, the answer uses the existing `final_text` terminal-message lease. Blank output, Gateway exception, unknown cost, and `BUDGET_EXHAUSTED` on the Chat single-call path must produce a visible corrective message and a non-success record; these terminal failures use ACP `end_turn` rather than Zed's content-policy `refusal` banner. Actual cancellation returns `cancelled`. In particular, `BUDGET_EXHAUSTED` is absent from today's `_PLANNING_TERMINAL_STOP_REASONS`, and today's single-call `create_response` has no planning-loop exception/unknown-cost handling; tests must cover both gaps. Context-admission refusal follows its existing contract. Never present a failed model response as a successful answer. Preserve the separately owned structured stop-reason metadata gap (`P11.25-FU-2`) and Zed refusal-rendering gap (`P9.8-FU-5`); this slice does not close them.

## Conversation and safety

Chat uses the same `ConversationState.prepare_admission`, sanitizer, 512 KiB byte cap, bytes/4 estimate, turn sequence, and `prepare_commit`/settlement as Agent. With no Context Engine, history remains full and unsummarised until the cap prevents admission. A successful Chat record has the sanitized user prompt, empty plan text, actual answer as completion text, the existing completed outcome, and `EffectState.NONE`. Terminal/cancelled records follow the existing settlement contract without inventing a successful answer. Do not add a second conversation log or a separate Chat capacity policy. Test switches Agent→Chat→Agent and several Chat turns for ordering and absence of duplicated current prompts.

The enforcement half remains the single authority for mutations. Chat must not request, execute, or report writes, shell commands, MCP side effects, or approval escalation. Tests exercise both an apparently benign question and adversarial prompts/workspace content that ask for mutation. Existing Agent behavior, including approval and guard checks, must remain intact.

## Integration and evidence

This slice changes `src/optimus/acp/spec.py` around session state, prompt admission/request construction, result updates, completion, and conversation commit; `src/optimus/acp/conversation.py` supplies the existing record/envelope and should not acquire a strategy or second cap. It also changes the non-AGENT runner/prompt boundary in `src/optimus/agent/runner.py`, `models.py`, and `prompts.py`. The sandbox-only context-floor work later touches `spec.py` admission/commit and the conversation record. At port time, diff and reconcile those seams explicitly; no sandbox source is copied into this branch and the two lanes' evidence remains separate.

Acceptance requires red-then-green focused tests, ACP schema conformance for both projections and setters, an independent `acpx` session/new → set_config_option/set_mode → prompt run, and a live installed-Zed Chat question with a visible prose answer and no plan card or mutation. The evidence must also show Agent is default, the two protocol projections stay synchronized, and Agent remains subject to its existing approval path. The user-facing result must be true with the Context Engine absent. The full-suite policy and prerequisites are in the implementation plan.
