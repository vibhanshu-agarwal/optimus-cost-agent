## Design and alternatives

Recommended: allow `GatewayToolDependencies.web_provider: WebToolProvider | None` without a default (retain dataclass ordering and explicit constructors); construct the bundle whenever the shared Redis URL and normalized domain policy are present. Instantiate Tavily only for a nonblank key. In `server.py`, add one private availability predicate `_serves_tool_path(path: str, dependencies: GatewayToolDependencies | None) -> bool` and use it in both `do_POST` and `_handle_post`. It accepts only existing tool paths with a bundle, and requires a non-None web provider for either web path. Thus a disabled web request can never fall through to chat/model dispatch. At the HTTP boundary, treat search and extract as unavailable when this field is `None`, using `_reject_unhandled_post()` so bounded draining, connection closure and request deadlines remain intact. At direct handler dispatch, preserve bearer authentication first and return the same 404 `{"error": "not found"}` for either unavailable web path, without touching policy/state/provider. Use explicit narrowing/guards before web-provider dereferences; do not add a `type: ignore` or nonfunctional provider placeholder.

Alternatives considered: (a) split the bundle and server into separate registration systems: unnecessary API churn for four existing routes; (b) construct an inert Tavily provider with an empty key: misrepresents capability and risks a late external request. Both are rejected as larger or less fail-closed. This mechanism is Codex's proposal for adoption, not an operator-selected implementation detail.

Configuration behavior (for ordinary well-framed requests):

| Redis URL | Normalized domain list | Tavily key | Package / OSV | Search / extract |
|---|---|---|---|---|
| present | nonempty | missing, empty or whitespace | Built; authenticated requests reach existing policy/state/providers | HTTP 404; no provider or state access |
| present | nonempty | present | Existing behavior unchanged | Existing behavior unchanged |
| missing or whitespace | any | any | All tool dependencies unavailable; existing fail-closed HTTP behavior | Same |
| any | empty after normalization | any | All tool dependencies unavailable; existing fail-closed HTTP behavior | Same |

Enabled routes keep authentication, validation, policy checks, result-domain validation, provenance, caps, usage/cost envelopes and sanitized failures. Do not reorder those protections. Disabled HTTP web routes retain the current unconfigured-route convention (early 404, with existing framing errors when applicable); direct handler calls still authenticate before route availability. Core model, identity, memory and observability routes remain unchanged. No local client keys are added: upstream provider credentials remain Gateway-owned.

LLD §9C.4 must distinguish implemented metadata independence from the unchanged target: its illustrative `ToolDependencies` listing and separate `extract: ExtractBackend` are not the shipped shape. Extraction remains Tavily-backed and unavailable without its key; label extract independence specified/not implemented and retain the target verbatim. Clarify the target table's ‘Always available’ metadata wording as subject to Redis/domain prerequisites. Do not mark the whole target design implemented. #361 owns documenting and completing the extract-custody handoff described in Prerequisites; #362 is only the proposed receiving issue until an authorized record explicitly accepts it.
